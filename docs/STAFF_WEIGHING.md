# Development staff weighing

This is a test workflow using simulated scale readings. Staff login, role checks and trip assignments are stored in PostgreSQL. The simulator is enabled only when DALUMAGA_STAFF_SIMULATOR=true and NODE_ENV is not production. The API must bind to 127.0.0.1 when the simulator is enabled.

The local API environment is in apps/api/.env. For the current Supabase development project it contains a path to the downloaded CA certificate. Node loads that certificate when the API process starts. Keep the certificate available at the configured path.

The sample accounts were generated by the seed script. On the development computer, open apps/api/.staff-demo-credentials.json to find the weigher, receiver and dispatcher usernames and passwords. This file is ignored by Git and should remain private. The data in it is for testing, not real employees.

Run from the project root:

```powershell
corepack.cmd pnpm db:status
corepack.cmd pnpm dev
```

Open http://localhost:5174 to sign in as dispatcher. Use an Android emulator with Expo SDK 54 to sign in as weigher or receiver. The sample crate named C044 is available for another walkthrough.

1. Sign in as the weigher with connectivity, then disconnect the emulator.
2. Select the available crate, read the simulated scale and save. The phone shows a pending reading.
3. On a second signed-in session, receive the same crate as the receiver and sync it.
4. Reconnect the first emulator and sync. The dispatcher can refresh the office screen to see the difference.

Sessions last 12 hours. After online sign-in and verification, a user can capture while the app remains active without connectivity. Queued events remain on the device after the app closes. Sign-out while offline clears the local session but cannot revoke the server session until it expires.

For real factory use, add secure device enrollment, protected offline access and retention, audited account provisioning and recovery, HTTPS for deployed clients, operational monitoring, independently verified hardware, and a security review. Do not use the simulated flow for employee or factory data.

## Device enrollment and recovery

Signing in on mobile enrolls an installation for that staff account. Its randomly generated device secret is stored with Expo SecureStore. The office page lists devices belonging to the signed-in account; match the device using the eight-character identifier shown on the phone. Select Revoke for a lost device. Revocation stops that device's server access and is checked when it next connects. Sign in from another device to regain access. Password reset and administrative account suspension are not yet implemented; development-only admin device revocation is described below.

A staff user may opt in to **Enable saved-session unlock** on a device with supported and configured biometrics. The cached session is protected by the device's biometric authentication. After restarting the app, **Unlock saved session** can show saved assignments and pending work, but recording another weight requires reconnecting and verifying the account and device. A single saved session is kept per installation; enabling it for another user replaces the saved session. Confirm shared-device procedures with the factory before a pilot.

Queued readings remain on the device when signing out. New readings use an encrypted SQLite database in a SQLCipher development build; a migrated legacy plaintext queue remains on the device as a recovery copy. Biometrics identify an enrolled device user, not a particular employee. The phone clock can be changed and offline revocation cannot be delivered until connectivity returns. These limitations prevent safe use with real staff or factory data. Secure offline storage, reliable offline session expiry, a shared-device policy, password recovery, HTTPS, independently verified hardware and a further security review are required before field use.

Apply migrations before starting the updated API:

```powershell
corepack.cmd pnpm db:migrate
corepack.cmd pnpm db:status
```

This changes the configured development database. Confirm `apps/api/.env` points to the intended database first. Previously signed-in mobile sessions must sign in again to enroll their device.


## Scan a crate (simulator)

The QR label contains the exact registered crate code, such as `C044`. Sign in online and download assigned crates first. Tap **Scan crate QR**, allow camera access and point the phone at the label. The selected code appears before weighing. If camera access is unavailable, type the exact code or choose a crate from the assigned list. Unknown, already recorded and ambiguous codes are rejected. Crate codes are case-sensitive. If the same crate appears in multiple assigned loads, ask the office to resolve it before recording; the app must not guess which load is intended. QR label content and this ambiguity policy are assumptions to verify with the factory.

The camera needs a physical device or an emulator configured with a camera image. With Expo Go, camera support is supplied by the installed Expo Go client; native builds also require the camera permission configured in app.json. Restart Metro after installing dependencies. Test denial of camera permission and the typed-code fallback as well as a successful scan.

This workflow remains a simulator. Existing plaintext queues are retained during encrypted migration; do not use real employee or factory data. Native-build migration testing, secure cleanup and a key recovery plan are still required.

## Encrypted staff queue: development build only

The staff queue now opens a SQLCipher database using a random key saved in SecureStore. New staff readings go into the encrypted database. If an existing plaintext staff queue is found in the **same app installation**, its rows and sync states are copied in one transaction and checked before the import marker is saved. The original plaintext queue is deliberately retained as a recovery copy. Do not use real staff or factory data until migration, cleanup, key loss and device security have been verified on native devices and the retained plaintext has been safely handled.

Expo Go does not include the required SQLCipher native library. Use Android Studio, an Android SDK and JDK 17 to build a development app with `corepack.cmd pnpm --filter @dalumaga/mobile exec expo run:android`, then start Metro with `corepack.cmd pnpm --filter @dalumaga/mobile dev`. An Expo Go installation and a standalone development app have separate Android app storage: the new app cannot automatically read the Expo Go queue. Sync all Expo Go sample readings first, verify them at the office, and keep Expo Go installed until then. Do not delete or clear app data to troubleshoot.

If the key is missing, invalid or a previously created encrypted database is unavailable, the app refuses to open the queue rather than replacing the key or creating an empty queue. Uninstalling the app or clearing its data can permanently remove the key and unsent readings. Recovery and production device management are not implemented. A native emulator check has been completed as described below; physical-device and end-to-end recovery testing are still needed. A successful JavaScript export alone is not evidence that the database is encrypted.

## Native validation and remaining cleanup design

A SQLCipher Android debug build was tested on an emulator with isolated synthetic data. A legacy pending event kept its ID and original timestamp during import; a second reading and the imported event remained pending after an offline process restart. Ordinary SQLite could not open a copy of the encrypted database without its key. When the test key was temporarily unavailable, the queue refused to open; restoring the original key recovered both events. A deliberately thrown error during import rolled back a real SQLCipher transaction, and retry imported each test event once. Both events then synced to a local mock endpoint after reconnection; a second sync sent no additional events. This test did not use a physical phone, an actual process kill mid-transaction, or the production backend.

The test used a local, generated Gradle override to use the installed NDK 27.1 for Android library modules; that override was removed after the test. A clean native build may also need Android NDK 27.0, depending on the toolchain. The normal application entry point and debug build were restored after testing.

**Proposed, not implemented: plaintext cleanup.** Before deleting a legacy queue, compare every original event's ID, actor, load, stage and immutable payload against a successfully reopened encrypted database, accounting for sync state changes. Stop if any record is missing or differs, if the key is unavailable, or if the legacy queue could still be written by another process. Record a durable cleanup decision and test interruption and retry, including the database's WAL and shared-memory files. Agree on a recovery and backup policy before deletion, and do not assume deleting a file securely erases flash storage. Expo Go and the standalone app have separate storage; handle the Expo Go queue by syncing and verifying its pending readings first. This design needs review and real-device tests before use with actual data.

## Encrypted queue end-to-end check

A separate synthetic crate was tested in the normal SQLCipher Android app against the configured development API. The pickup was saved offline, the app was force-stopped and restarted offline, and the user signed in after reconnecting. The pending pickup reached the backend once. A separate sample receiver recorded the receipt through the API; the office dashboard displayed 18 kg pickup, 15 kg receipt and a 3 kg decrease. The debug build used a bundled normal app for the offline restart. Without a saved biometric session the normal app requires online sign-in before a user can view or sync pending work. This was an emulator test, not a physical-phone or real-scale test.

For a separate migration-interruption test, an isolated native SQLCipher test database used the same import function with 300 synthetic records. The emulator app was force-stopped during the transaction; on restart, the partial import had rolled back and a retry imported all 300 records. This test did not interrupt an actual user's legacy database.

`compareLegacyEvidence` in `apps/mobile/src/queue-security.ts` provides a non-destructive comparison of legacy and encrypted records, including missing, changed, unsynced and duplicate IDs. It does not open databases, verify server evidence or prevent concurrent writes, and its result does not authorize deletion. Automatic cleanup and key recovery remain unimplemented; the plaintext recovery copy is retained.

## Lost phone and unavailable queue recovery (development simulator)

The sample office app supports an `admin` account searching for a field worker's exact username and revoking one registered phone for the reason lost, stolen or compromised. The server enforces the role and restricts targets to field accounts without manager or admin roles; it records the admin, device, account, reason and time in the audit log. The endpoint is disabled unless `DALUMAGA_STAFF_SIMULATOR=true` and `NODE_ENV` is not production. The seed script does not provision an admin; test admin accounts must be created in a separate development database. Decide who can approve and perform recovery before a pilot.

If a phone is lost, the staff member should tell the office using an agreed contact method. The administrator confirms the person's identity and which device is affected, revokes the correct phone, and checks the device list. Once the device reconnects, the server rejects its existing sessions. A replacement phone can enroll after the user signs in with valid credentials. This does not disable the account or change its password. If credentials may also be compromised, an authorized administrator must disable the account using a reviewed operational process; password reset, administrative account suspension and secure admin provisioning are not implemented in the app.

The office can see readings already accepted by the server. An offline reading saved only on the lost phone cannot be reconstructed by the server. Mark the affected collection as requiring investigation through existing operational procedures; do not manufacture a weight or present the absence of a reading as proof of theft. The system does not yet provide a recovery case, lost-reading reconciliation or secure access to encrypted device backups.

If the phone is available but the encrypted queue cannot be opened, the mobile app tells staff to keep the phone, avoid uninstalling or clearing app data, and contact the administrator. Do not create a new key or delete either database to bypass the error. The administrator should preserve the device and investigate using an approved process. If the original key is permanently lost, encrypted unsynced records are not recoverable from the server; a retained plaintext legacy copy may contain older records but does not necessarily contain later readings. There is no supported automated key recovery or legacy restore workflow. Device lock, password compromise, key availability, network status and database migration must be assessed individually before taking action.

ASSUMPTION: One trusted administrator is authorized to manage field devices for the single-factory simulator. Confirm real factory boundaries, identity verification, independent approvals, administrator provisioning and the acceptable recovery process before building this for field use.
